The Final Review and Debrief

The final review evaluates the repository at the commit that exists at the deadline. It runs the prototype from its README, reads the paper and the portfolio, watches the presentation, and ends with the debrief and a feedback file.

The steps

Each step leaves a file in your repository, and every file stays there. The student commits the student's files. The professor commits only the feedback files, in feedback/.

What the review checks

  1. Navigation. Every required item is reachable from the root README. Work I can find only by searching costs organization points. Work I cannot find is missing.
  2. The prototype runs. I follow the README as written, from a clean clone. A step that needs something only you have (a personal API key, an account) is recorded as blocked, not failed, and the debrief demonstration covers it.
  3. The synthesis prototype. It delivers what your proposal promised, or the README explains the change.
  4. The areas. SS and at least two other areas are each necessary to the prototype, and the paper accounts for all four.
  5. The data. The data meet the four conditions, and the provenance table is in the README.
  6. The package. The paper runs 5 to 10 pages, the video runs 5 to 15 minutes, and the slides are present.

Before you submit

  1. Open the root README on GitHub and follow every link.
  2. Clone the repository into a new folder and follow the prototype README from the first step. The prototype must start.
  3. Check that the final version of each deliverable is clear, with no duplicates that compete for it.
  4. Check that no credentials, API keys, or private data are anywhere in the commit history.

After the review I add exactly one file to your repository, feedback/final-project.md. Nothing else in the repository comes from me.

Dates, submission steps, and scoring are on the WTClass pages. How the debrief runs is in the debrief guide.
