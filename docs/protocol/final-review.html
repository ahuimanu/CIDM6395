Protocol · The final review

The final review and debrief

I review your repository as it stands at your last commit before the deadline. I check that every required file is in place, run the prototype from its README, read the portfolio and the paper, and watch the presentation. The debrief, the only scheduled meeting in the course, follows once you have delivered.

The steps

Only the first and last steps change your repository: your final commit, and my feedback/final-project.md.

What I check

I start by opening each required path listed in Your repository. A file at another path is misplaced, which costs organization points, and a file I cannot find is missing. Then I clone the repository into an empty folder and follow prototype/README.md as written. If a step needs something only you have, such as a personal API key, I record the run as blocked rather than failed and ask you to run it in the debrief.

With the prototype running, I check that it delivers what your proposal promised (or that the README explains the change), that SS and at least two other areas are each necessary to it, and that its data meet the four conditions, with the provenance table in the README. Last, I check the package: the paper runs five to ten pages, the video runs five to fifteen minutes, and the slides are there.

Before your final commit

  1. Open each required path on GitHub and make sure the file is there.
  2. Clone the repository into a new folder and follow prototype/README.md from the first step until the prototype starts.
  3. Remove or move any draft that sits beside a required file.
  4. Search the whole commit history for credentials, API keys, and private data.

Specific details about dates, submission, and scoring are in WTClass. How the debrief runs is in the debrief guide.
