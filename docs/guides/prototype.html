Guide · The synthesis prototype

The synthesis prototype

The synthesis prototype is what you build this term: a time-bounded slice of a larger project, built as a minimum viable product. It has to run on real data when I follow your README.

The full project and the prototype

Your proposal describes two things. The full project is what one competent person could build in about a year of full-time work. It needs all four areas, because a project that one area could finish alone does not test synthesis. The synthesis prototype is the part of it you can finish in the weeks after your proposal is approved.

Treat the prototype as a sample of the full project rather than a smaller project of its own. It carries real data along one complete path, from the source to something a user sees and acts on, through SS and at least two of BA, DM, and CN. Each step can be thin. Every step has to run. Two shapes fail here: one area built well with the others stubbed, and every component built halfway. Neither leaves a path I can follow from the data to the result, and that path is the evidence that the areas work together.

Which areas count

An area counts when the prototype breaks without it. SS is required, since the prototype has to run and SS is what runs. Add at least two of the other three. Figure 01 shows where a prototype like that sits; Figure 02 follows one example through three views.

Data

I hold the data to four conditions.

First, relevance. The data come from the domain of your problem, and every field you use connects to a decision or an operation there. A dataset picked because it was easy to download, with a problem invented afterward to fit it, does not qualify.

Second, accountability. Someone outside the course answers for the original data: an agency, a firm, a research group, or your employer with written permission. Your README carries a provenance table with who produced the data, the terms of use, the date you got it, and each change you made to it. If nobody answers for the data, nobody can check a claim you make from it.

Third, availability. I have to be able to get the same data you used, so commit the data or a script that retrieves it.

Fourth, quality, which here means transactional variety: many records, of more than one kind, produced by real activity over time and carrying the gaps, duplicates, and late corrections real activity leaves. Dirty data is fine, because cleaning it is DM work. A tidy table of a few hundred rows is not fine, because it leaves DM with nothing to do.

Kaggle and other sample datasets

Kaggle, the UCI repository, and the datasets that come with textbooks are good for learning a technique and poor for a capstone. Someone else has already framed the problem and done the cleaning. The file is a frozen snapshot, so SS has nothing to ingest and CN has nothing to protect. The source is often an uncited copy of someone else's data. And thousands of public notebooks use the same file, which means I cannot tell which decisions are yours.

Government and transactional data usually clear all four conditions. An agency stands behind the data and publishes a data dictionary, and event-level records (flights, loan applications, complaints, payments) give every area real work. Even an aggregate series from the Federal Reserve or BEA is better evidence than most Kaggle files, since an agency answers for every number in it; use a series like that as context, joined to an event source. The WTClass page "Data Sources for the Capstone" lists 40 sources I have checked.

You may use synthetic data if you generate it from a documented real reference, commit the generator, and use the result only to supplement real data or to stand in for data you can show you cannot get. Synthetic data invented from scratch only tells you what you told the generator.

How it runs

Write the prototype in Python. The interface can be a command-line program, a web app (Streamlit, for example), or a Jupyter notebook. A notebook should call the data layer, the pipeline, and the controls, not contain them.

I do not accept a prototype built only in Excel, and I discourage macros. Excel does not run on Linux, a macro written on Windows often breaks on a Mac, and Git cannot show me what changed inside a macro workbook. Any tool other than Python needs my approval in the proposal cycle, and I approve only tools that run on Windows, macOS, and Linux.

At review I clone your repository into an empty folder and follow prototype/README.md from the top. When a step needs something only you have, such as a personal API key, I note it and ask you to run the prototype for me in the debrief, for at least five minutes.
