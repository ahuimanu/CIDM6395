The Synthesis Prototype

The prototype is the working artifact at the center of the capstone. It is a working sample of a larger project, built on real data, and it runs from its own instructions. This guide explains the constraints on its scope, its data, and the way it runs.

A sample of the full project

As used in this course, the full project is the work one competent person could do in about one year. It needs all four areas. The synthesis prototype is the part you build this term. The two are judged by different tests.

The full project must need all four areas, because a project that one area could finish alone does not test synthesis. The synthesis prototype must fit in the weeks after the proposal, and it must show that the full project can work. For this reason the synthesis prototype is a sample of the full project, not a smaller project. It carries real data along one complete path through the areas the prototype integrates. Each step can do less than the full project would do, but every step runs.

A student may object, correctly, that a prototype that does a little in every area looks less impressive than one area done well. The capstone does not ask for the most impressive area. It asks for evidence that the areas work together, and one complete path is that evidence. A prototype that builds each component halfway has no path from start to end, so it shows effort but not viability.

Four conditions on the data

The data must meet four conditions. Each one protects a different part of the argument the prototype makes.

  1. Relevance. The data come from the domain of the problem, and each field you use traces to a decision or an operation in that domain. A dataset chosen because it was easy to download, with a problem invented to fit it, fails. So does a toy problem whose answer matters to no one.
  2. Accountability. Someone outside the course answers for the original data: an agency, a firm, a research group, or your employer with written permission. Your README records who produced the data, the terms of use, the date you got it, and each change you made. If no one answers for the data, no one can check a claim made from it.
  3. Availability. You can get the data now, in the volume the prototype needs, and a reviewer can get the same data again. The repository holds the data, or a script that retrieves it.
  4. Quality. The data have transactional variety: many records of more than one kind, made by real activity over time, with the defects real activity makes. The data need not be clean, because cleaning is part of the DM work. One tidy table of a few hundred rows gives DM nothing to do.

Why not Kaggle

Sample datasets on Kaggle, the UCI repository, and in textbooks are good material for learning a technique. Most are poor material for a capstone, for five reasons. Someone else framed the problem. Someone else did the DM work. The data are a frozen snapshot, so SS has nothing to ingest and CN has nothing to protect. The provenance is often a copy of an uncited source. And thousands of public notebooks use the same file, so a reviewer cannot tell which decisions are yours.

Government and transactional datasets usually meet all four conditions. An agency answers for the data and publishes a data dictionary, and an event-level record (a flight, a loan application, a complaint, a payment) gives every area real work. Even an aggregate series from the Federal Reserve or BEA is better evidence than most Kaggle files, because an agency answers for every value. Use such a series as context, joined to an event source. The WTClass page "Data Sources for the Capstone" lists 40 checked sources.

Synthetic data is admissible only when it is generated from a documented real reference, the generator is in the repository, and it supplements real data or replaces data you show you cannot use. Synthetic data made from nothing shows only the patterns the generator put in.

How it runs

The prototype is written in Python, with one of three interfaces: a command-line program, a web application such as Streamlit, or a Jupyter notebook. A notebook is acceptable as the interface but not as the whole system. The data layer, the pipeline, and the controls exist outside it, and the notebook calls them.

A prototype built only in Excel is not accepted, and Excel macros are discouraged. Excel does not run on Linux, a macro that works on Windows can fail on a Mac, and Git stores a macro workbook as a binary file that a reviewer cannot compare between commits. Any tool other than Python needs my approval, and I approve only tools that run on Windows, macOS, and Linux.

The prototype README states the Python version, the dependencies file, how to get the data, and the command that starts the prototype. At review, I clone the repository and follow the README from the first step. In the debrief I may ask you to demonstrate the prototype live for at least five minutes.
