Systems Development (SS)

Systems Development builds the software that runs. In the capstone it is the one area every prototype must include, because the prototype must function.

What SS does in a working system

SS designs and builds the software that makes the other areas' work run as a system: the program that loads the data, the application a user opens, the job that runs on a schedule, the tests that show it works. Its output is software that someone other than the author can start and use.

SS is required in every prototype for one reason: the prototype must function, and software is what runs. That requirement does not put SS at the center of the design. SS can act at the start of the flow (ingestion), at the end (delivery), or both.

Where SS meets the other areas

In Figure 01, SS overlaps each of the other three areas, and each overlap is a recognizable practice:

  • SS with DM: the persistence layer. Software built over managed data.
  • SS with BA: decision delivery. Analysis delivered to a user through software.
  • SS with CN: secure delivery. Software that is secured and deployed safely.

SS in the prototype

In a prototype, SS is the code a reviewer starts from the README. Its test in the proposal: remove SS, and nothing runs. Show SS in the repository as Python source with a dependencies file, a README that starts the prototype on a clean machine, and, where you can, tests. The run rules are on the prototype guide.
